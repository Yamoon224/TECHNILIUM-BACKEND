# Technilium — Backend

API REST Laravel du projet Technilium, une marketplace de produits technologiques (Afrique francophone) et de son backoffice de gestion — catalogue, vendeurs, stocks, commandes, facturation, comptabilité, livraison, SAV.

Architecture en **monolithe modulaire** : chaque domaine métier vit sous `app/Modules/<Nom>/` avec ses propres migrations, routes, modèles, actions et tests, communiquant par événements plutôt que par jointure SQL directe.

Dépôts liés : [TECHNILIUM-WEB-STORE](https://github.com/Yamoon224/TECHNILIUM-WEB-STORE) (vitrine) · [TECHNILIUM-WEB-BACKOFFICE](https://github.com/Yamoon224/TECHNILIUM-WEB-BACKOFFICE) (équipe/vendeurs)

## Stack

- Laravel 12, PHP 8.3
- MySQL 8 (dev/prod via `docker compose`), SQLite accepté en local
- Sanctum (jetons API), Spatie Permission (rôles)
- Pest (Unit/Feature/Integration/Architecture), Larastan, Pint
- Swagger/OpenAPI généré depuis les attributs PHP

## Démarrage rapide

```bash
docker compose up -d      # MySQL, Redis, Meilisearch, Mailpit (sans Docker : adaptez DB_*/REDIS_* dans .env)
composer install
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
php artisan serve          # http://localhost:8000
```

Documentation API interactive : `php artisan l5-swagger:generate` puis http://localhost:8000/api/documentation

Compte de démonstration après le seed : `admin@technilium.app` / `password` (rôle `administrateur`), plus un petit catalogue (2 catégories, 3 produits avec offre publiée).

## Qualité

```bash
composer test          # Pest : Unit / Feature / Integration / Architecture
composer test:coverage
composer lint           # Pint (style)
composer analyse        # PHPStan/Larastan niveau 6
```

## État d'avancement

Implémenté :

- **Identity** — inscription/connexion/déconnexion par jeton Sanctum, rôles.
- **Catalog** — galerie de photos par produit (`POST /api/v1/admin/products/{id}/images`, `POST .../images/{image}/cover`, `DELETE .../images/{image}` ; 8 photos au plus, JPG/PNG/WebP 2 Mo max, SVG refusé, nom de fichier choisi par le serveur, disque `public` : lancer `php artisan storage:link` ; la première photo est la couverture ; `image_url` et `images` dans le catalogue public), catégories, produits, variantes, offres multi-vendeurs avec modération, stock (palliatif en attendant le module Inventory).
- **Orders** — panier → commande en paiement à la livraison uniquement (pas de passerelle de paiement), machine à états simplifiée (pending → confirmed → shipped → delivered, ou cancelled), décrément de stock atomique et verrouillé pour éviter la survente. Communique avec Catalog via un contrat public (`Catalog\Application\Contracts\CheckoutGatewayInterface`), jamais via ses modèles Eloquent.
- **Shared** — objets-valeur `Money`, `Currency`, `Quantity`, `TauxTVA`, `Sku`, `NumeroSerie` utilisés dans tout le code.

- **Vendors, Inventory, Payments, Shipping** — candidature/modération vendeurs, mouvements de stock, paiements (COD / mobile money confirmés manuellement), expéditions.
- **Invoicing** — factures numérotées de façon séquentielle (`FAC-AAAA-000001`), TVA extraite du TTC (taux `INVOICING_VAT_PERCENT`, 18 % par défaut), documents immuables, avoir total (`AV-AAAA-000001`) pour toute correction. Endpoints `/api/v1/admin/invoices` (rôles comptable / administrateur). `GET /api/v1/admin/invoices/{id}/pdf` produit le PDF (dompdf, vue Blade `invoicing::document`) d'une facture ou d'un avoir : lignes, remise, HT / TVA / TTC, montant arrêté en lettres. L'émetteur vient de `INVOICING_COMPANY_NAME/_ADDRESS/_PHONE/_EMAIL/_LEGAL` (RCCM/NCC à fournir par l'entreprise, jamais inventés) ; tout le texte est échappé et les ressources distantes sont désactivées. **Émission automatique** : à la confirmation d'une commande (événement `OrderStatusChanged`), la facture est émise sans intervention ; jamais deux fois, et une commande déjà facturée (même annulée par un avoir) est laissée au comptable ; un échec n'empêche jamais la commande d'avancer ; désactivable avec `INVOICING_AUTO_ISSUE=false`. Côté client connecté : `GET /api/v1/customer/orders/{orderNumber}/invoices` et `GET /api/v1/customer/invoices/{id}/pdf`, strictement limités aux commandes du client (404 sinon, y compris pour une commande invité ou un compte du personnel).

- **Accounting** — grand livre en écriture seule (partie double, SYSCOHADA : 411, 571, 585, 4431, 701), écritures générées de façon synchrone et idempotente par les événements `InvoiceIssued` / `PaymentSettled` (facture, avoir, encaissement, remboursement). Lecture : `/api/v1/admin/accounting/entries` et `/trial-balance`.
- **Payouts** — reversements vendeurs : ventes livrées hors délai de retour (`PAYOUTS_RETURN_DELAY_DAYS`, 7 j) moins commission (`PAYOUTS_COMMISSION_PERCENT`, 10 %), une commande n'est jamais reversée deux fois, écritures 701 → 706 / 4011 puis 4011 → 585. Les lignes de commande portent le `vendor_id` de l'offre (base des sous-commandes par vendeur) et la commande a un `delivered_at`. Endpoints `/api/v1/admin/payouts`.
- **Returns** — dossiers RMA (`requested → accepted → received → refunded`, refus possible avant acceptation ou après contrôle) sur commande livrée, dans le délai `RETURNS_WINDOW_DAYS` (7 j), montant plafonné à ce qui reste remboursable. Un remboursement émet un avoir (partiel) sur la facture vivante via `ReturnRefunded`, et réduit proportionnellement le reversement du vendeur ; un retour ouvert bloque le reversement. Les avoirs peuvent désormais être partiels (plusieurs par facture, plafonnés au solde). Endpoints `/api/v1/admin/returns`.
- **Espace vendeur** (`/api/v1/vendors/me/*`, module Vendors) — synthèse, commandes (uniquement les lignes du vendeur et sa part), relevés de reversement, offres. Le vendeur est toujours déduit du compte authentifié (jamais d'un paramètre) ; un reversement d'un autre vendeur répond 404. Lecture seule hors offres : les commandes n'ont pas encore de statuts par vendeur.
- **Sous-commandes** (module Orders) — le checkout crée une sous-commande par vendeur (et une pour le stock Technilium), chacune avec son statut (`pending → confirmed → shipped → delivered`, `cancelled`) et sa date de livraison. Le statut de la commande est dérivé du moins avancé de ses parts, `partial` indique des parts à des stades différents. `POST /orders/{n}/sub-orders/{id}/transition` (personnel) et `POST /vendors/me/orders/{n}/ship` (le vendeur expédie sa part) font avancer une part ; une transition de la commande entière se répercute sur ses parts. Payouts paie chaque part livrée sans attendre les autres vendeurs. Les commandes sans sous-commande (antérieures) restent gérées comme avant.
- **Code de confirmation de livraison** — un code à 6 chiffres est généré à chaque commande (chiffré en base), visible uniquement du client (`/orders/{n}?phone=`, `/orders/mine`, réponse du checkout), jamais des endpoints du personnel. `POST /admin/shipments/{id}/deliver` exige `confirmation_code` ; 5 codes faux verrouillent l'expédition (`code_locked`). Une commande antérieure sans code est acceptée telle quelle.
- **Boucle des retours** — un retour peut nommer ses articles (`items: [{offer_id, quantity}]`, contrôlés contre la commande et les autres retours) ; `receive` avec `restock: true` remet les articles en stock (mouvement audité), `false` les laisse hors stock (produit abîmé). Un retour remboursé rembourse aussi le paiement : Payments gère désormais les remboursements partiels (`POST /admin/payments/{id}/refund` avec `amount` optionnel, plusieurs remboursements par paiement, une écriture comptable chacun ; le paiement passe à `refunded` une fois tout rendu).

- **Reporting** (lecture seule, `/api/v1/admin/reports/*`, rôles administrateur / comptable) — tableau de bord direction (CA, commandes, panier moyen, ventes par jour, top produits, commandes par statut, finance : encaissé / remboursé / commissions / reversé / dû aux vendeurs, retours et taux de retour, alertes : commandes bloquées et stock bas), ventes par vendeur, export CSV des ventes (`;`, UTF-8). **Marge de Technilium** (`GET /admin/reports/margin`, `margin.csv`) : marge brute sur les **seules ventes en propre** (stock de Technilium) des commandes **livrées** dans la période — chiffre d'affaires **HT** (TVA `INVOICING_VAT_PERCENT`) moins coût des ventes au coût moyen **ligne par ligne** (mémorisé à la livraison). La remise d'un coupon est supportée par Technilium mais seule la part qui tombe sur ses **propres lignes** entre dans cette marge (au prorata de leur valeur ; la part sur les lignes d'un vendeur tiers est un coût de promotion marketplace, hors marge) ; les ventes de vendeurs tiers et les commissions sont exclues. Ventilation par produit (meilleure marge d'abord) et par jour, taux de marge, **alerte de qualité** si du chiffre d'affaires n'a aucun coût enregistré (marge alors surestimée), retours de la période affichés **à côté, non déduits** (un remboursement couvre toute la commande, pas seulement les lignes en propre). Période : 30 derniers jours par défaut, 366 jours max. Chaque module expose un contrat de statistiques (`OrderStatsInterface`, `PaymentStatsInterface`, `PayoutStatsInterface`, `ReturnStatsInterface`) ; Reporting n'accède à aucun modèle d'un autre module. Montants en XOF uniquement.

- **Promotions** — codes promotionnels (pourcentage 1-100 ou montant fixe), avec achat minimum, fenêtre de validité, plafond global et par client (téléphone du checkout). `POST /coupons/quote` (public, limité) donne la remise d'un panier sans l'utiliser ; `POST /orders` accepte `coupon_code` et consomme le code **dans la transaction de la commande** (verrou : la dernière utilisation ne peut pas être prise deux fois, et un échec de commande ne consomme rien). Gestion : `/admin/coupons` (marketing / administrateur ; un coupon se désactive, ne se supprime pas). **Règle de partage : la remise est à la charge de Technilium** — `orders.subtotal_amount` reste ce que le client doit (net), `discount_amount` / `coupon_code` sont tracés, les sous-commandes et donc les reversements restent au prix affiché (la remise vient en déduction du CA 701 de Technilium), la facture est établie sur le net (TVA sur le net) avec la remise indiquée, un retour d'articles est remboursé au prorata de ce qui a été payé.

- **Notifications** — SMS / WhatsApp au téléphone du checkout, et **e-mail** à l'adresse facultative `customer_email` du checkout (validée, jamais visible d'un vendeur ; pas d'e-mail si elle est absente ; pilote `log` par défaut, `NOTIFICATIONS_EMAIL_DRIVER=mail` pour envoyer réellement via les réglages `MAIL_*`), à la commande (avec montant et code de livraison), à chaque changement réel de statut (confirmée, expédiée, livrée, annulée — une part qui avance sans changer le statut de la commande ne déclenche rien) et au remboursement d'un retour. Une ligne par message (`notifications_log`, unique par événement + référence + canal : un événement rejoué n'envoie rien de plus), envoi par job **après validation de la transaction** (une commande annulée n'envoie rien), un échec de livraison est enregistré sans jamais affecter la commande et se relance depuis `/admin/notifications/{id}/retry`. **Le fournisseur n'est pas encore choisi** : le pilote `log` journalise sans envoyer (numéro masqué) ; brancher un fournisseur = une classe `NotificationChannelInterface` + une ligne dans `ChannelResolver` + `NOTIFICATIONS_SMS_DRIVER`. Journal : `/api/v1/admin/notifications` (support / administrateur).

- **Audit** (`/api/v1/admin/audit`, administrateur seul) — chaque requête de modification (POST/PUT/PATCH/DELETE) faite par un compte backoffice (équipe et vendeurs, pas les clients ni les invités) est enregistrée : qui (id, nom, rôles), quoi (méthode, chemin, route), quand, d'où (IP), avec quel résultat — **y compris les refus (403/422)**. Le corps de la requête est conservé avec les secrets masqués (mots de passe, jetons, codes de confirmation, cartes…). Écriture après l'envoi de la réponse (ne ralentit ni ne fait échouer la requête). Journal **en écriture seule** et **chaîné** : chaque entrée est signée (HMAC avec la clé de l'application) avec la signature de la précédente ; `GET /admin/audit/verify` détecte une entrée modifiée ou supprimée directement en base. Filtres : utilisateur, méthode, chemin, échecs seulement, période.

- **Customers / Support** — tickets de support. **Client** (`/api/v1/support/tickets`, compte connecté, limité en débit) : ouvrir un ticket (catégorie, sujet, message, commande concernée **vérifiée comme appartenant au compte**), lister les siens, lire la conversation, répondre. Le ticket d'un autre client répond 404, comme un ticket inexistant ; les notes internes et l'identité des agents ne sont jamais exposées. **Équipe** (`/api/v1/admin/tickets`, support / administrateur) : file filtrable (statut, priorité, assigné à moi / non assigné, **en retard**, client, texte), conversation complète, réponse ou **note interne**, statut, priorité, prise en charge. La conversation fait vivre le statut (réponse équipe → attente client ; réponse client, même sur un ticket résolu → à traiter ; ticket clos → plus de réponse possible). Délai de première réponse par priorité (`SUPPORT_RESPONSE_HOURS_*`, 2 h / 8 h / 24 h) : un ticket sans première réponse hors délai est « en retard ».

- **Customers / Avis vérifiés** — un client ne peut donner un avis que sur un produit **qu'il a reçu** (un de ses comptes a une commande *livrée* qui le contient ; commande invitée, expédiée, annulée ou d'un autre client : refusé) et **une seule fois** par produit. Lecture publique `GET /reviews/products/{id}` (avis publiés, note moyenne à une décimale, répartition ; seulement prénom + initiale, jamais d'identifiant ni de numéro de commande) ; `GET /reviews/products/{id}/eligibility` (le formulaire s'affiche-t-il ?), `POST /reviews`, `GET /reviews/mine`. **Modération automatique** : un avis propre est publié aussitôt, un avis contenant un lien, un e-mail, un numéro de téléphone ou un mot de `REVIEWS_BANNED_WORDS` attend une décision humaine (l'automatique ne rejette jamais). **Modération manuelle** (`/admin/reviews`, support / marketing / administrateur) : file avec les avis en attente d'abord, publier, rejeter avec motif (montré à l'auteur), retirer un avis publié, le rétablir. Catalog expose `ProductLookupInterface` et Orders `deliveredOffersForCustomer` : aucun modèle d'un autre module n'est touché.

- **Procurement (achats)** — `/api/v1/admin/*` (responsable achats / administrateur). **Fournisseurs** (coordonnées, conditions de paiement en jours, délai ; désactivés, jamais supprimés). **Bons de commande** : brouillon → commandé → reçu en partie / reçu (ou annulé, tant que rien n'est reçu) ; seul le **stock propre** de Technilium s'achète (pas l'offre d'un vendeur tiers), une offre une seule fois par bon. **Réception** en une ou plusieurs fois avec contrôle ligne par ligne : quantités *acceptées* (entrent en stock, mouvement audité) et *refusées* (retour fournisseur, rien en stock ni en comptabilité), jamais plus que le reste à recevoir, verrouillée contre les réceptions simultanées. **Frais d'approche** (transport, douane, manutention) répartis sur les marchandises reçues au prorata de leur valeur, somme exacte à l'unité près même en réceptions partielles, et **rattrapés** à la réception suivante si le frais est saisi après la première. **Coût moyen pondéré** par offre recalculé à chaque réception (stock existant × coût actuel + arrivage au coût complet), valorisation `GET /procurement/stock-valuation`. **Factures fournisseurs** (numéro unique par fournisseur, échéance = date + conditions du fournisseur), règlements partiels sans dépasser le reste dû, **dettes** `GET /procurement/payables` (total, échu, par fournisseur). **Comptabilité automatique** par événements : réception → 311 stock / 4012 fournisseurs + 4013 frais d'approche ; règlement → 4012 ou 4013 / 521 banque ; **livraison d'une commande** → coût des ventes 601 / 311 au coût moyen, uniquement pour les lignes du stock propre (jamais pour un vendeur tiers), idempotent ; le coût reconnu est mémorisé par commande. **Retour client remis en stock** (`restock: true` à la réception) → le coût des ventes est **repris** (311 / 601 au crédit) au coût moyen des unités retournées, **plafonné à ce qui a été reconnu** pour la commande moins ce que les retours précédents ont déjà repris (un coût moyen monté depuis ne peut pas dépasser le coût réellement constaté), une seule reprise par retour même si l'événement est rejoué ; un retour non remis en stock (produit abîmé) ou une ligne de vendeur tiers ne reprend rien.

Pas encore implémenté : numéros de série à la réception, retour fournisseur / RMA fournisseur et avoirs, achats en devises étrangères et écarts de change, demande de prix, suggestions de réapprovisionnement, marge par catégorie / canal / vendeur et marge nette des retours (la marge actuelle est brute, par produit et par jour), fiche client unifiée, réponse du vendeur à un avis, questions/réponses sur la fiche produit, photos dans les avis, note affichée sur les cartes du catalogue, note de qualité des vendeurs, segmentation, liste de blocage clients, canaux e-mail/WhatsApp pour les tickets, notification du client à la réponse de l'équipe, écritures manuelles, journaux achats/banque, états de synthèse comptables, audit « avant/après » des valeurs modifiées (seule la requête est tracée), événements de sécurité hors requête (connexions échouées), fournisseur SMS/WhatsApp réel, e-mail client (non collecté au checkout), notifications push, relances automatiques d'échecs, préférences et consentement marketing, promotions automatiques (remises catalogue, ventes flash, offres groupées), remise supportée par le vendeur, parrainage/fidélité, rapports de marge/stock valorisé/achats/livraisons/SAV, Audit, Procurement, Customers, Notifications ; preuve de livraison alternative (signature, photo) et déverrouillage d'une livraison bloquée, retours par sous-commande (un retour exige aujourd'hui la commande entière livrée), exécution réelle du remboursement chez l'opérateur mobile money / carte (aujourd'hui enregistré, pas exécuté), régularisation d'un remboursement postérieur au reversement, échange/réparation/garanties par numéro de série, PDF des documents.

## Conventions

SOLID — contrôleurs fins, un cas d'usage = une classe `Action`, validation dans des `FormRequest`, formatage dans des `API Resource`. Montants toujours en entiers (plus petite unité monétaire), jamais en flottant. Tests d'architecture (Pest Arch) imposant les frontières entre modules.
